# HowToBVCryptLib.md

## BVCryptGameLib を使った証明のためのガイドライン

このドキュメントは、`BVCryptGameLib` を使って計算量的安全性の証明（擬似ランダム性、Transfer/closure、Next Bit 予測不可能性など）を進める上での設計思想と、証明を書く／レビューする際に守るべきポリシーをまとめたものである。ライブラリ自体のAPIリファレンスではなく、「このライブラリをどう使うべきか、何を避けるべきか」という運用上の指針として位置づける。

---

## 1. ライブラリのコンセプト

BVCryptGameLib は、暗号ゲームの確率的な議論を `PMF` と `do` 記法で記述し、その変形を `calc` チェーンでつなぐことで、人間が読んで追える形の証明を作ることを目的としたライブラリである。

典型的に必要になる変形は次のようなパターンである。

- `do` 文の中で、サイコロを振った結果を実際には使っていない場合、そのサンプリングを除去できる。
- 1つの `BitVec n` から乱数を得ることは、`n = a + b` のとき `BitVec a` から乱数を得て `BitVec b` から乱数を得て組にしたものと同型である。

これらを可能な限り「上位の変形」として提供し、下位のビット演算や確率の総和計算に降りずに証明を進められるようにすることが、このライブラリの狙いである。

`BitVec` についても `++` やビット演算をできるだけ避け、同型（`Equiv`）で議論できるように設計されている。

ライブラリは以下のようにレイヤー分けされている。

- **Layer 1: BitVec 構造層（同型のカタログ）** — `bv_split`/`bitvec_equiv`、`bv_cast_equiv`、`bv_split3_i` など、`BitVec` の形に関する同型を集めた層。
- **Layer 2: 汎用 PMF 基盤層** — `PMF.prod`、一様分布が同型で保存されることを示す `U_map_equiv` など、`BitVec` に依存しない一般的な PMF の道具。
- **Layer 3: BitVec 一様分布層（`U n`）** — `U_split`、`U_join`、`U_split_i` など、`n` ビットの一様分布 `U n` の分解・結合を扱う層。
- **Layer 4: ゲーム変形層** — `bind_bind_do`、`map_bind_do` など、`do` 記法での bind/map/pure の入れ替えを行う層。加えて `Pr`、`Pr_bind`、`Pr_prediction_logic` など、predictor/distinguisher 変換でよく使う確率計算のパターンをあらかじめ定理化したものを含む。

新しい証明に取り組む際は、まず「これは既存のどのレイヤーの組み合わせで表現できるか」を検討することから始める。

## 2. 中核ポリシー：安易に低レベルへ逃げない

過去の経験上、AI（本アシスタントを含む）は放っておくと、`PMF` のモナド演算をすべて `tsum` や `Finset.sum` に展開して `ite` の場合分けを力業で処理する、あるいは `U` に関する議論を `BitVec` のビット演算（`toNat`、`getLsbD` など）に落として「あとは `omega` で示せます」と提案しがちである。これは一見すると証明が「動く」ように見えることがあるが、次の理由からこのライブラリの設計思想に反する。

- 一度 `tsum`/`Finset.sum` やビット演算のレベルに降りると、その証明はその場限りの使い捨て計算になり、他の場面で再利用できない。
- 既存の `Equiv` のカタログ（Layer 1〜3）を経由せず、車輪の再発明をすることになる。
- `calc` チェーンで人間が追える証明ではなく、tactic の塊になり可読性が失われる。

### 2.1 正しいアプローチ

新しい証明課題に対しては、次の順序で考える。

1. `BitVec` の形に関する話であれば、Layer 1 の `Equiv` を組み合わせて表現できないか検討する。既存の分割パターンで足りなければ、同じ抽象度で Layer 1 に新しい補題を追加することを検討する。
2. 一様分布の分解・結合の話であれば、Layer 3 の `U_split` 系の定理を使う。無ければ既存と同じ `calc` スタイルで新設する。
3. `do` 記法における bind/map/pure の入れ替えが必要であれば、Layer 4 の `_do` 系の補題を使う。足りなければ同種の補題を追加する。
4. 確率の値そのもの（`Pr`）を計算する必要がある場合に限り、Layer 4 に既に用意された `Pr_bind` などの、総和処理を内部に持つ補題を経由する。**ここが `tsum`/`Finset.sum` を扱うことが許される、事実上唯一の合法的な出口である。** それ以外の場所で `tsum` に直接手を出すべきではない。

### 2.2 ライブラリは不完全であってよい

必要な補題が存在しないことは当然あり得る。その場合は、安易に低レベルな計算へ逃げるのではなく、既存の補題と同じ抽象度・同じ `calc` スタイルで新しい補題を該当レイヤーに追加する。たとえば `h_split_U` や `U_split3_i` は、その手本となる型のパターンである。

- `U_cast` で型を揃える。
- 分解定理（`U_split` など）を適用する。
- `map_bind_do`/`map_pure_do` で `map` を `do` ブロックの中に押し込む。
- 定義の展開によって両辺の一致を示す。

ビット演算的な処理がどうしても避けられない場合（`BitVec.eq_of_toNat_eq` などを使わざるを得ない場合）は、それを **Layer 1 の内部**（`Equiv` の `left_inv`/`right_inv` の証明など、同型を定義するその場所）に一度だけ閉じ込め、それより上位のレイヤーからは決して見えないようにする。

## 3. 依存型計算の罠を避けることも重要な目的である

`BitVec n` は自然数 `n` を型のインデックスに持つ依存型である。そのため、たとえば `BitVec (n+m)` と `BitVec (m+n)` は、`n+m = m+n` という命題自体は `omega` で瞬時に示せるにもかかわらず、Lean の型としては異なるものとして扱われる。

この依存性がもたらす困難は、単に「見た目の抽象度が低い」という問題にとどまらない。より本質的な技術的困難がある。

- ビット演算のレベルで議論しようとすると、「`a : BitVec (n+m)` と `b : BitVec (m+n)` が同じビットパターンを持つ」という主張は、そもそも `a = b` という式を書くこと自体が型エラーになる。これを書くには `a.cast (proof) = b` のように明示的な `cast` を挟む必要があり、その証明項が式の中に埋め込まれる結果、以降の `simp`/`rw` がその `cast` のせいで刺さらなくなったり、`cast` 同士の合成によって証明項が肥大化したりする。
- 一方、`Equiv`（同型）で議論すれば、`bv_cast_equiv (h : n = m) : BitVec n ≃ BitVec m` のように「型の違い」を一つの関数として抽象化できるため、`n+m` と `m+n` が異なる型であること自体は問題にならない。`Equiv` の適用は通常の関数適用に過ぎず、依存性はその場で吸収される。

このライブラリで `bv_cast_equiv`、`U_cast` などが多用されているのは、まさにこの罠を回避するためである。「長さの違う `BitVec`（あるいは `U`）同士を直接『等しい』と主張する」のではなく、「`Equiv`（あるいは `map`）で明示的に橋渡しする」という形にすることで、依存型の等式証明特有の困難を避けている。

### 3.1 危険信号としての `eq_of_toNat_eq` / `eq_of_getLsbD_eq`

ここで重要な訂正がある。**「長さが同じ `BitVec` 同士の等式であれば `BitVec.eq_of_toNat_eq` や `BitVec.eq_of_getLsbD_eq` を使うこと自体は問題ない」というのは誤りである。** 実際には、証明の中にこれらの補題が登場すること自体が危険信号である。

- これらの補題が出てきた時点で、既に「`Equiv`/`do`/`map` の世界」から降りて、ビットパターンの直接比較に入ってしまっている。
- そこに入ると、決まって「あとは `omega` で閉じられるはず」という楽観的な提案が出てくるが、実際には `BitVec.toNat_cast`、`toNat_append`、`getLsbD_...` 系の simp 補題が複雑に絡み合い、期待通りには `omega` や `simp` が閉じず、VS Code 上で延々と赤線（エラー）が出続けるという事態を繰り返してきた。

### 3.2 根本原因は定理のステートメントの立て方にある

この罠に落ちる根本原因は、多くの場合、**定理のステートメント自体に `++`（`HAppend.hAppend`）を登場させてしまうこと**にある。

- ステートメントに `++` を書いてしまうと、それを扱うためには結局 `BitVec.extractLsb'_append_...` のようなビットレベルの補題を証明の中で呼ばざるを得なくなり、そこから自然に `eq_of_toNat_eq`/`eq_of_getLsbD_eq` へと転がり込んでしまう。
- そのため、このライブラリでは `U_split`/`U_join` のような核心定理は `bv_join n m (x, y)` という **`Equiv` を使った表現**で書かれている。`++` を使った版（`U_join_append` など）は、あくまで `rfl` または既存の等式一本で導出される派生形として、後付けで用意されているに過ぎない。**`++` 版を主定理として証明しようとしないことがポイントである。**
- `bv_split`/`bv_split3` などの Layer 1 の内部では `extractLsb'` や `++` の扱いが避けられないが、それは同型を定義するその場所に一度だけ閉じ込められており、それ以降の Layer 2〜4 のどの定理のステートメントにも `++`/`extractLsb'`/`getLsbD` を持ち込まない、という設計になっている。

### 3.3 実践への反映

新しい定理を提案・証明する際は、以下を徹底する。

1. まず、ステートメントに `++`、`extractLsb'`、`getLsbD` を**書かないこと**を目指す。書きたくなった場合は、それが「既存の `bv_join`/`bv_split` 系の `Equiv` で表現し直せないか」を検討すべきサインである。
2. 証明の途中で `BitVec.eq_of_toNat_eq` や `BitVec.eq_of_getLsbD_eq` を書きたくなったら、そこで一度立ち止まる。まず Layer 1 に既にある同型の `left_inv`/`right_inv`、あるいは射影定理（`bv_split3_i_proj_pre`/`bv_split3_i_proj_bit`/`bv_split3_i_proj_bool` のようなもの）を使って回避できないかを探す。
3. どうしても新しい構造的な同型が Layer 1 に存在せず、低レベル証明が避けられない場合は、その証明を **新しい Layer 1 の補題として一度だけ書き**、以降はその補題を再利用する形にする。証明本体の中に埋め込まない。
4. 「`omega` で閉じるはず」という提案を安易にしない。依存型の長さに関する等式（`n + m = m + n` など）は `omega` で示せても、`BitVec` の**値**としての等式は `omega` だけでは閉じないケースが大半であるため、この種の提案自体を控える。

## 4. まとめ：証明作業における振る舞いの指針

新しい暗号証明のタスクに取り組む際、以下の順序で考える。

1. まず、既存の Layer 1〜4 の補題の組み合わせで目的の定理を表現し直せないかを検討する。
2. 足りない場合は、既存の補題と同じ抽象度・同じ `calc` スタイルで新しい補題を該当レイヤーに追加することを提案する。
3. `tsum`/`Finset.sum`/`ite` の場合分けや、`getLsbD`/`toNat` によるビット演算に落とす提案は、Layer 1 の同型を定義する内部実装、および Layer 4 の `Pr` 系補題を経由する場合を除き、原則として行わない。
4. 定理のステートメントに `++`/`extractLsb'`/`getLsbD` を持ち込まないことを最優先する。
5. 証明の途中で `BitVec.eq_of_toNat_eq`/`eq_of_getLsbD_eq` が必要になりそうだと気づいた時点で、それを証明本体に埋め込む前に、「これは Layer 1 に新しい同型・射影補題として抽出すべきではないか」を先に提案する。
6. 「`omega` で閉じられるはず」という楽観的な見通しを安易に提示しない。
